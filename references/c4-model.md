# C4 모델 정리

원문: https://c4model.com (Simon Brown, [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/)). 아래는 원문의 정의를 한국어로 요약하고, 인프라 그림에 적용할 때의 해석을 덧붙인 것이다. 해석은 "적용" 표시로 구분한다.

## 1. 추상화 다섯 가지

C4는 "무엇을 그릴지"를 먼저 정하고 모양은 나중에 정한다(abstraction-first). 같은 추상화를 줌인·줌아웃해서 여러 그림을 만든다.

| 추상화 | 정의 |
|---|---|
| Person | 시스템을 쓰는 사람, 역할, 페르소나 |
| Software System | 누군가에게 가치를 주는 가장 높은 단위. 하나 이상의 컨테이너로 이루어짐 |
| Container | **애플리케이션 또는 데이터 저장소.** 전체 시스템이 동작하려면 실행 중이어야 하는 것. 서버 측 웹 앱, SPA, 모바일 앱, 콘솔 앱, 서버리스 함수, 데이터베이스, 블롭 저장소, 파일 시스템, 셸 스크립트 등 |
| Component | 컨테이너 안에서 코드를 묶는 단위. 책임과 인터페이스를 가짐 |
| Code | 클래스·인터페이스·함수 등 |

컨테이너에 대한 원문의 주의점:
- C4의 Container는 **Docker 컨테이너가 아니다.** 이름이 겹칠 뿐 배포 방식을 뜻하지 않는다.
- JAR·DLL·어셈블리는 코드 묶음이라 컨테이너가 아니다.
- 서버 측 앱과 JavaScript가 많은 클라이언트 측 앱은 프로세스가 달라 별개의 컨테이너다.
- S3·RDS 같은 외부 호스팅 저장소도 그 시스템이 쓰는 데이터 저장소라면 컨테이너로 그린다.

## 2. 그림 종류

핵심 네 가지와 보조 세 가지가 있다. 원문은 "대부분의 팀에는 시스템 컨텍스트와 컨테이너 그림이면 충분하다"고 한다.

| 그림 | `data-c4-diagram` | 범위 | 주 요소 | 보조 요소 | 독자 |
|---|---|---|---|---|---|
| 시스템 컨텍스트 | `context` | 시스템 하나 | 범위 안 시스템 | 연결된 사람·외부 시스템 | 비기술자 포함 모두 |
| 컨테이너 | `container` | 시스템 하나 | 그 시스템의 컨테이너 | 컨테이너와 직접 연결된 사람·시스템 | 개발자·운영자·아키텍트 |
| 컴포넌트 | `component` | 컨테이너 하나 | 그 컨테이너의 컴포넌트 | 연결된 컨테이너·사람·시스템 | 개발자·아키텍트 |
| 코드 | `code` (기하만 검사) | 컴포넌트 하나 | 클래스·인터페이스·함수·DB 테이블 등 | | 아키텍트·개발자 |
| 시스템 지형 | `landscape` | 조직·부서 | 여러 시스템 | 사람 | 모두 |
| 동적 | `dynamic` | 특정 기능·시나리오 | 상호작용 순서 | | 기술자 |
| 배포 | `deployment` | **배포 환경 하나** (운영·스테이징 등) | 배포 노드, 시스템·컨테이너 인스턴스 | 인프라 노드 (DNS·LB·방화벽 등) | 아키텍트·개발자·인프라·운영 |

컴포넌트 그림과 코드 그림은 **선택 사항**이다. 원문은 컴포넌트 그림을 "가치가 있을 때만, 오래 둘 문서라면 자동 생성을 고려"하라고 하고, 코드 그림은 "가장 중요하거나 복잡한 컴포넌트가 아니면 권하지 않으며 IDE·모델링 도구로 필요할 때 생성"하라고 한다. 코드 그림이 꼭 필요하면 UML 클래스 그림이나 ERD 같은 기존 표기를 쓴다.

동적 그림은 특정 기능·시나리오에서 시스템·컨테이너·컴포넌트가 실행 중에 어떻게 협력하는지 보여 준다. **상호작용에 번호를 매겨 순서를 나타낸다.** 자유 배치(협력 스타일)와 일렬 배치(시퀀스 스타일) 둘 다 된다. 복잡하거나 반복되는 흐름에만 아껴 쓴다.

시스템 지형 그림은 특정 시스템에 초점을 두지 않은 컨텍스트 그림이다. 조직 안의 사람과 시스템을 모두 보여 준다.

컨테이너 그림에는 **클러스터링, 로드밸런서, 복제, 장애 조치 같은 배포 세부를 넣지 않는다.** 환경마다 달라지기 때문이다. 그런 것은 환경별 배포 그림에 그린다.

배포 노드는 소프트웨어가 실행되는 곳이다. 물리 장비, 가상화(IaaS·PaaS·VM), 컨테이너화(Docker 컨테이너), 실행 환경(DB 서버·앱 서버)이 모두 배포 노드가 될 수 있고, 서로 중첩할 수 있다(예: 서버 > Docker > 컨테이너 인스턴스).

## 3. 표기 규칙

C4는 표기법을 강제하지 않는다(UML·ArchiMate도 가능). 대신 아래 규칙을 지키라고 권한다.

그림:
- 제목에 **그림 종류와 범위**를 쓴다 (예: "쇼핑몰 · 컨테이너"). 이 스킬은 제목을 그림 위에 그리지 않고 `<title>` 과 문서 캡션에 쓴다.
- 범례(key)를 둔다. 모양, 색, 테두리, 선 모양, 화살표 머리의 뜻을 설명한다.
- 약어와 줄임말은 모든 독자가 알 만하거나 범례에서 풀어 쓴다.

요소:
- 유형을 명시한다 (예: `[Container: PostgreSQL]`).
- 핵심 책임을 한눈에 알 수 있는 짧은 설명을 붙인다.
- 컨테이너와 컴포넌트에는 기술을 명시한다.

관계:
- 선 하나는 **한 방향** 관계 하나다.
- 선마다 의도를 설명하는 글자를 붙이고, 그 설명은 화살표 방향과 맞아야 한다. "사용한다(Uses)"처럼 막연한 말은 피한다.
- 컨테이너 사이 관계에는 기술·프로토콜을 쓴다 (예: `[JSON/HTTPS]`).

색: 정해진 색은 없다. 일관되게 쓰고, 색약과 흑백 인쇄를 고려해 색만으로 뜻을 전하지 않는다.

## 4. 검토 질문

원문의 검토 체크리스트를 요약했다. `check-svg.mjs` 가 자동으로 보는 것은 (자동) 으로 표시했다. 나머지는 그림을 보고 직접 판단한다.

일반
- 제목(`<title>`, 문서 캡션)이 있는가 (자동: `<title>`). 그림 종류와 범위를 알 수 있는가 (일부 자동)
- 범례가 있는가 (자동)

요소
- 모든 요소에 이름이 있는가 (자동)
- 모든 요소의 유형(추상화 수준)을 알 수 있는가 (자동: 유형 표기 유무, Level 혼합)
- 모든 요소가 무엇을 하는지 알 수 있는가 (설명 유무는 자동, 내용의 질은 직접)
- 해당되면 기술 선택을 알 수 있는가 (자동: 컨테이너·컴포넌트)
- 약어·색·모양·아이콘·테두리·크기의 뜻을 알 수 있는가 (색·점선 테두리가 범례에 있는지만 자동)

관계
- 모든 화살표에 의도 설명이 있는가 (자동). 설명이 방향과 맞는가 (그려진 방향은 자동, 문장 뜻은 직접)
- 해당되면 기술·프로토콜을 알 수 있는가 (자동: 컨테이너 사이)
- 약어·색·화살표 머리·선 모양의 뜻을 알 수 있는가 (선 색·점선이 범례에 있는지만 자동)

## 5. 적용: 인프라·플랫폼을 그릴 때

원문은 애플리케이션을 중심으로 설명한다. 조직이 운영하는 인프라나 플랫폼을 그릴 때는 아래처럼 해석한다.

**범위 정하기**
- 플랫폼 팀이 운영하는 공용 시스템(이미지 저장소, 차트 저장소, 모니터링, 클러스터)을 그릴 때는 **플랫폼 자체를 하나의 Software System** 으로 둔다.
- 그 위에 올라가는 앱은 플랫폼의 컨테이너가 아니다. 각자 별도의 Software System 이다. 컨텍스트·컨테이너 그림에서는 "배포된 앱들" 하나로 묶어 외부 시스템으로 그려도 된다.

**어디에 무엇을**

| 대상 | 컨테이너 그림 | 배포 그림 |
|---|---|---|
| 이미지 저장소, 패키지·차트 저장소, 메트릭 수집 서버, 로그 저장소, 대시보드 | 컨테이너 (각각) | 해당 서버·Docker 노드 안의 컨테이너 인스턴스 |
| DB | 컨테이너 (데이터 저장소) | DB 서버 노드 안의 인스턴스 |
| Kubernetes API 서버 | 플랫폼이 제공하는 기능이면 컨테이너 | 컨트롤 플레인 노드 안 |
| Kubernetes 클러스터, 네임스페이스 | 그리지 않음 (배포 세부) | 배포 노드 (중첩) |
| 물리 서버, VM, 클라우드 인스턴스 | 그리지 않음 | 배포 노드 |
| Docker 엔진 | 그리지 않음 | 배포 노드 (실행 환경) |
| Pod·Deployment 로 뜬 앱 | (앱 시스템의 컨테이너) | 컨테이너 인스턴스 |
| 로드밸런서, 방화벽, DNS | 그리지 않음 | 인프라 노드 |
| VPN 게이트웨이 | 그리지 않음 | 인프라 노드 |
| 메트릭·로그 수집 에이전트 | 플랫폼이 실행해야 동작하는 것이면 컨테이너 | 대상 서버 노드 안 |

**배포 그림은 환경마다 하나.** 운영과 개발이 같은 서버에 섞여 있으면 그 사실을 제목이나 노드 설명에 적는다.

## 6. 흔한 실수

- **Level 섞기:** 컨텍스트 그림에 컨테이너가 나오거나, 컨테이너 그림에 서버·클러스터가 나온다. 검수기 C5 가 잡는다.
- **여러 컨테이너를 상자 하나로 묶기:** 예를 들어 "모니터링 (메트릭 수집 · 로그 저장 · 대시보드)" 를 상자 하나로 그리는 경우다. 셋은 따로 실행되는 앱이므로 컨테이너 그림에서는 상자 셋으로 그린다.
- **개수를 요소로 그리기:** "앱 Pod 24개" 는 배포 그림의 인스턴스 묶음으로는 괜찮다. 하지만 컨테이너 그림의 요소는 아니다.
- **Docker 컨테이너 = C4 컨테이너로 보기:** Docker 로 띄운 저장소는 C4 컨테이너가 맞지만, 이유가 Docker 라서는 아니다. 실행 중이어야 하는 앱·저장소라서다. Docker 엔진 자체는 배포 노드다.
- **유형 칸에 다른 정보 넣기:** `[Person]` 자리에 "내부망 또는 VPN" 처럼 위치를 적으면 유형을 알 수 없다. 위치·조건은 설명 줄에 쓴다.
- **"사용한다" 관계:** 무엇을 하려고 부르는지 동사로 쓴다 (예: "이미지를 받는다", "로그를 보낸다").
- **방향이 뒤집힌 설명:** 화살표는 A→B 인데 설명은 "B 가 A 에게 보낸다" 라고 쓴 경우.
- **양방향 화살표:** 요청과 응답은 하나의 관계다. 요청 방향 하나로 그린다. 실제로 서로 먼저 부르는 관계면 선을 둘로 나눈다.
